# Project Overview
## Cloud Before Code: Learn Cloud Computing Through a Business Story

---

## Title and Subtitle

**Cloud Before Code**
*Learn Cloud Computing Through a Business Story*

---

## Abstract

Cloud Before Code is an original, scenario-based curriculum that teaches beginner cloud-computing vocabulary through one evolving fictional business story. Learners follow LunchRush, a small food-ordering and delivery business, as it moves from a local operation to a cloud-connected service. Each of the eight lessons begins with a plain-language business challenge before any technical terminology is introduced. After working through the problem in everyday language, learners encounter accurate definitions, work through a hands-on activity, and practice explaining the solution twice — once without jargon, once using correct vocabulary. A personal jargon journal helps learners build and retain their own cloud-computing glossary. No coding, cloud accounts, or software installation is required. All core activities work on paper or in editable documents. The curriculum is designed for one college student to complete, present, and evaluate. Three lessons are fully developed into ready-to-use lesson packs; the remaining five are provided as concise outlines. A pilot evaluation plan supports optional small-scale testing with three to five volunteers.

## Problem Statement

Introductory cloud-computing resources often begin with technical terminology before learners have any context for why the concepts matter. This creates a barrier for students and nontechnical adults who want foundational cloud literacy but do not have a software engineering background. Vocabulary-first instruction can produce surface-level recognition of terms without genuine conceptual understanding. Cloud Before Code addresses this gap by grounding each term in a business problem the learner has already tried to solve in plain language.

---

## Audience

**Primary audience:** Students and nontechnical adults who

- have no prior cloud-computing experience,
- may be unfamiliar with programming or networking concepts,
- want to understand cloud terminology without feeling overwhelmed, and
- are not required to write code, create cloud accounts, or install software.

**Secondary audience:** Instructors or facilitators seeking a ready-to-use, activity-based introductory unit that requires minimal setup and no paid services.

---

## Purpose

The purpose of Cloud Before Code is to help beginner learners build accurate, working knowledge of introductory cloud-computing vocabulary through a consistent scenario-based teaching sequence. The curriculum prioritizes genuine conceptual understanding over memorization and equips learners to explain cloud concepts in both plain and technical language.

---

## Measurable Learning Objectives

By the end of the three fully developed lessons, learners will be able to:

**Lesson 2 — Storage**

1. Distinguish between object storage and a database in the context of a small business scenario and explain the simplified distinction.
2. Sort at least five fictional business data items into appropriate storage categories and provide a written justification for each choice.
3. Define *storage*, *object*, *bucket*, and *database* in their own words using the jargon-journal template.
4. Explain the storage decision to a nontechnical business owner using plain language and to a technical teammate using correct vocabulary.

**Lesson 3 — Compute Options**

5. Describe the purpose of a virtual machine, a container, and serverless compute in beginner-friendly terms.
6. Use decision cards to compare at least three deployment options for a given scenario and state one trade-off for each.
7. Explain that *serverless* means the learner does not manage servers directly — not that no servers exist.
8. Explain the compute decision using both plain and technical language.

**Lesson 6 — Identity and Access**

9. Distinguish authentication (verifying identity) from authorization (deciding what is permitted).
10. Create a permissions table that assigns appropriate access levels to four business characters based on a stated business policy.
11. Define *authentication*, *authorization*, *IAM*, *least privilege*, and *shared responsibility* using the jargon-journal template.
12. Explain the access-control decision using both plain and technical language.

## Exclusions

This project does **not** include:

- A working web application, mobile application, or chatbot.
- Live cloud infrastructure of any kind.

## Distinctive Design Features

**1. Explain it before you name it**
Every lesson begins with a business problem described in plain language. Learners attempt to describe or choose a solution before the technical vocabulary is introduced. This reduces the cognitive barrier of encountering unfamiliar jargon without context.

**2. Explain it twice**
After completing each main activity, learners practice explaining the solution in two ways:
- To Jordan (the business owner) without technical jargon.
- To Alex (the technology helper) using correct vocabulary.

This dual-explanation task reinforces vocabulary use in context and surfaces gaps in understanding.

**3. The jargon journal**
For selected terms in each lesson, learners complete a five-part entry:
- *The technical term is:*
- *In my own words, it means:*
- *At LunchRush, we would use it when:*
- *One limitation of the analogy is:*
- *A question I still have is:*

Analogies are used to support understanding, not to replace accurate definitions. Each analogy includes an explicit statement of where it stops being accurate.

## Feasibility for a Student Project

Cloud Before Code is designed to fit within the scope of a single college student's semester project. Specific feasibility factors include:

- **No technical infrastructure:** All deliverables are text-based Markdown documents. No software installation, cloud provisioning, or coding is required to produce or use the materials.
- **Lightweight tooling:** The project uses only a text editor and optionally a Markdown previewer. All activity materials work on paper.
- **Bounded scope:** Three lessons are fully developed; five are concise outlines. This creates a complete and presentable product without requiring full development of all eight lessons.
- **Self-contained evaluation:** The pilot plan is designed for three to five volunteers over a single session, using instruments already included in the project.
- **Clear deliverable list:** The production checklist separates minimum required submission items from optional enhancements, so a student can prioritize efficiently.
- **No paid services:** The project incurs no cost for the creator or for learners.
